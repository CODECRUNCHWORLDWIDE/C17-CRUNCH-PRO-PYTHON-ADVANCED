# Week 10 — Metaprogramming, Descriptors, and Metaclasses

> *Every Python class you have ever written is itself an instance of a class. `type(int)` is `type`. `type(SomeUserClass)` is also `type`. The fact that "the type of a type is a type" is the philosophical core of Python's data model — and the door, once you walk through it, opens onto a workshop full of power tools. A class decorator can rewrite a class definition at the moment it is created. The `__init_subclass__` hook, defined by PEP 487 and merged into Python 3.6 in 2016, lets a base class react when any subclass is declared — without writing a metaclass. A descriptor — the protocol that powers `@property`, `@classmethod`, `@staticmethod`, and `inspect.Signature` underneath — is the answer to the question "what actually happens when I write `obj.attr`?" A metaclass is the answer to "and what if I want to control class creation itself?" These four mechanisms form a ladder of escalating power. The honest engineering judgement, which this week aims to instil, is **how far up the ladder to climb for any given problem** — and the answer is, for almost every real problem, **not as far as the textbooks suggest**. PEP 487 retired most of the legitimate use cases for metaclasses. Class decorators retired most of the rest. We will spend the week building one small library — a validated-model toolkit — four times, once with each mechanism, and we will measure the cost of each in lines of code, in readability, in error messages when things go wrong, and in cooperation with type checkers.*

Welcome to Week 10 of **C17 · Crunch Pro Python Advanced**. Last week you shipped a package to TestPyPI. This week we go to the other end of the abstraction stack: how Python itself constructs the classes that compose your package. The lecture material here is dense — three lecture notes, roughly 1,800 lines of prose — because the data model rewards careful reading, and because the gulf between "I have heard of descriptors" and "I can write one from memory that cooperates correctly with `inspect` and with `__set_name__`" is wider than it looks. The exercises, by contrast, are short and pointed. The mini-project is the synthesis: you implement a validated-model library four ways, you benchmark them, and you write a one-page decision tree that you would hand a junior teammate who has just been told "use a metaclass for this" and is trying to figure out whether to push back.

The thesis is a hierarchy. The right order to *think* about metaprogramming in 2026 — from cheapest and most legible to most powerful and most invasive — is **class decorator, then `__init_subclass__` / `__set_name__`, then descriptors, then metaclasses**. Class decorators (functions that take a class and return a (usually) modified class) are syntactically lightweight, work with every type checker, compose naturally with other decorators, and cover the overwhelming majority of real "do something at class creation time" needs. `@dataclass` is the canonical example; `@attrs.define`, `@pydantic.dataclasses.dataclass`, and `@functools.total_ordering` are others. **PEP 487** (Martin Teichmann, accepted 2016, merged in Python 3.6) added two new hooks to the language — `__init_subclass__` and `__set_name__` — explicitly to remove the need to write a metaclass for "the most common things people write metaclasses for: registry patterns, subclass validation, descriptor naming." It worked. Most libraries that defined a metaclass in 2015 do not need one in 2026. Descriptors — the protocol of `__get__`, `__set__`, and `__delete__` — are the next step up; they are how `@property` works, how `@classmethod` works, how `@staticmethod` works, how `inspect.signature` reads function signatures, and how every ORM defines its column types. The "Descriptor HowTo Guide" by Raymond Hettinger, free at <https://docs.python.org/3/howto/descriptor.html>, is the canonical reference and is required reading this week. Metaclasses are the top of the ladder: a class whose instances are themselves classes. The right answer is **almost always "you do not need one"** — but on the rare occasion that you do (ABC registration, enum member harvesting, the `Protocol` machinery in `typing`), they are the only mechanism that works.

The standards are the spine. **PEP 3115** (Talin, 2007) defined `__metaclass__` as a class-statement keyword argument (the `class Foo(Base, metaclass=Meta):` syntax) for Python 3, retiring the Python-2 `__metaclass__ = ...` class-body attribute. **PEP 487** (Martin Teichmann, 2016) added `__init_subclass__` and `__set_name__`. **PEP 560** (Ivan Levkivskyi, 2017) added `__class_getitem__` and `__mro_entries__`, the hooks that make `List[int]` and `Generic[T]` work without a metaclass. **PEP 657** is unrelated (column information in tracebacks). The data-model chapter of the language reference — <https://docs.python.org/3/reference/datamodel.html> — is the official source; sections 3.3.3.4 (the descriptor protocol) and 3.3.3.6 (`__init_subclass__`) are the relevant subsections. Hettinger's "Descriptor HowTo Guide" is the unofficial source. Together they are about 250 pages of careful reading. Budget two hours for the first pass and a third hour for the second pass after you have built the worked example.

The worked example is a **validated model library**. You declare a class like `class User(Model): name: str = StringField(max_length=50); age: int = IntField(min_value=0)`, and the library validates assignments, produces helpful error messages, supports a `.to_dict()` round-trip, and integrates with type checkers. You build this four times.

**Version one** uses a **class decorator**. `@validated_model` walks the class's annotations, replaces each annotated attribute with a property that validates on assignment, and adds an `__init__` and `__repr__`. The whole thing is about 80 lines. It looks like `@dataclass`. It cooperates with type checkers because the decorator returns the same class (no metaclass surprises). It is the right answer for 80% of real cases.

**Version two** uses **`__init_subclass__` and `__set_name__`**. `class Model: def __init_subclass__(cls, **kwargs): ...` reacts when any subclass is declared. `class StringField: def __set_name__(self, owner, name): self._name = name` learns its own attribute name at class-creation time (a thing that was *impossible without a metaclass* before PEP 487). The base class participates in the protocol via `__init_subclass__`; the field-descriptor objects participate via `__set_name__`. The result is about 90 lines. It is more flexible than the decorator (it composes with inheritance for free; subclasses inherit the protocol naturally). It is the right answer when the decorator version starts feeling cramped — typically when you have a hierarchy of models.

**Version three** uses **full descriptors**. Each `StringField` is a descriptor with `__get__`, `__set__`, and `__set_name__`. The validation logic lives in `__set__`. The instance storage is in `instance.__dict__[self._name]`. This is more powerful than the property-based decorator version (a descriptor can hold per-instance and per-class state independently; it can be overridden per-subclass; it integrates with `inspect.getmembers`). It is the right answer when fields need behaviour beyond "validate on assignment" — when, for example, you want a `CachedField` that computes on first access and caches, or a `ComputedField` that depends on other fields. This is also, not coincidentally, what Django models, SQLAlchemy columns, and Pydantic v1 fields are under the hood.

**Version four** uses a **metaclass**. `class ModelMeta(type): def __new__(mcs, name, bases, namespace): ...`. The metaclass intercepts class creation, harvests the field definitions, builds an `__init__` from the field list, attaches a `_fields` registry to the class. This is the path SQLAlchemy 1.x took. It is the path Django models take. It is the path `enum.Enum` takes. It is the most powerful approach — and the most expensive. Metaclass conflicts (you cannot inherit from two classes whose metaclasses are unrelated) are a real cost. Type-checker support is genuinely worse than for the other three (mypy and pyright both have special-cased support for `@dataclass` and `__init_subclass__`; metaclass-based DSLs need explicit `__class_getitem__` workarounds or a `mypy` plugin). We build this version anyway, because **the only way to learn that you do not need a metaclass is to write one and feel the friction**.

The deliverable for the week is the four-mechanism library, plus a benchmark that compares (1) class-definition time, (2) instance-creation time, (3) attribute-set time, (4) memory-per-instance across the four implementations, plus a **one-page decision tree** that explicitly answers "given problem X, which mechanism do I reach for and why?" The benchmark is small (a few hundred microseconds of timing) but the discipline of measuring instead of speculating is the point.

## Learning objectives

By the end of this week, you will be able to:

- **Articulate** the four-step ladder of metaprogramming power — class decorator, `__init_subclass__` + `__set_name__`, descriptors, metaclass — and pick the lowest step that solves the problem at hand. Cite PEP 487.
- **Read** and write a class decorator from scratch. Write `@validated_model` that turns annotated attributes into validating properties. Compare your output to `dataclasses.dataclass` source: <https://github.com/python/cpython/blob/main/Lib/dataclasses.py>.
- **Implement** `__init_subclass__` in a base class. Articulate why PEP 487 added it (Martin Teichmann's rationale: <https://peps.python.org/pep-0487/#rationale>). Cite the data-model reference: <https://docs.python.org/3/reference/datamodel.html#object.__init_subclass__>.
- **Implement** `__set_name__` on a descriptor. Articulate the bug it fixes (descriptors that needed to know their attribute name had to be assigned twice, once with the name and once as the attribute, before PEP 487).
- **Write** a non-data descriptor (`__get__` only), a data descriptor (`__get__` + `__set__`), and an `__set_name__`-aware descriptor. Predict for each whether instance `__dict__` shadows it. Cite Hettinger's HowTo: <https://docs.python.org/3/howto/descriptor.html>.
- **Explain** how `@property` is itself a descriptor (read `Lib/types.py` and `Lib/functools.py`; `property` is implemented in C, but the Python equivalent is in the HowTo).
- **Explain** how `@classmethod` and `@staticmethod` work as descriptors (the canonical interview question; Hettinger gives the Python implementation in the HowTo).
- **Write** a metaclass from scratch. Articulate the contract of `__new__(mcs, name, bases, namespace)` vs. `__init__(cls, name, bases, namespace)`. Articulate `__prepare__` and when it matters (rarely — enum member ordering, mostly).
- **Diagnose** the canonical metaprogramming bugs: (1) descriptor that does not implement `__set_name__` and is named manually wrong; (2) class decorator that returns a *new* class and breaks `isinstance`; (3) metaclass conflict on multiple inheritance; (4) `__init_subclass__` that mutates `cls` and surprises a subclass; (5) `super().__init_subclass__(**kwargs)` forgotten, which silently breaks cooperative multiple inheritance.
- **Measure** the runtime cost of the four mechanisms. Use `timeit` and `tracemalloc`. Articulate which differences matter at scale and which are noise.
- **Cooperate** with type checkers. Articulate which of the four mechanisms each of mypy and pyright understands natively, which need `typing.dataclass_transform` (PEP 681, 2022; <https://peps.python.org/pep-0681/>), and which require a mypy plugin.
- **Decide**. Given a real problem (a validated-config loader, an ORM column system, an event-emitter base class, an enum-like construct), pick the right rung of the ladder and defend the choice in two sentences.

## Topics covered

- **The class statement is an expression** — `class Foo(Base, metaclass=Meta, **kwargs): ...` is sugar for `Foo = Meta('Foo', (Base,), namespace, **kwargs)`. The data model section 3.3.3 spells this out. Read it once.
- **Class decorators** — functions of signature `Callable[[type], type]`. The canonical example is `@dataclass`. Composable, type-checker-friendly, the right default. We write one from scratch.
- **PEP 487** — `__init_subclass__` and `__set_name__`. The two hooks that retired most metaclass use cases in 2016. Martin Teichmann's rationale is worth reading.
- **Descriptors** — the `__get__` / `__set__` / `__delete__` / `__set_name__` protocol. Data vs. non-data descriptors. Instance `__dict__` precedence. The implementation of `@property`, `@classmethod`, `@staticmethod`, `@functools.cached_property`.
- **Metaclasses** — `type`, `__new__` vs. `__init__`, `__prepare__`, `__call__`. The MRO conflict that occurs on multiple inheritance. The (small) set of legitimate use cases that survive the existence of `__init_subclass__`.
- **Cooperation with type checkers** — `typing.dataclass_transform` (PEP 681). What mypy and pyright each understand natively. The `__class_getitem__` and `__mro_entries__` hooks (PEP 560).
- **A four-way comparison** — same library, four implementations, measured costs.
- **The decision tree** — when to reach for which mechanism. Written down so you can hand it to a teammate.

- Read [PEP 487](https://peps.python.org/pep-0487/) end-to-end (~25 minutes). Martin Teichmann, 2016. The single most consequential metaprogramming PEP of the last decade.
- Read the [Descriptor HowTo Guide](https://docs.python.org/3/howto/descriptor.html) by Raymond Hettinger end-to-end (~60 minutes, two passes). The canonical reference; free; in the official docs.
- Read [the data-model reference, section 3.3.3](https://docs.python.org/3/reference/datamodel.html#customizing-class-creation) — about 2,500 words on `__init_subclass__`, `__set_name__`, descriptors, and metaclasses. The official source.
- Read [the `dataclasses` source in CPython](https://github.com/python/cpython/blob/main/Lib/dataclasses.py) — about 1,400 lines. The reference implementation for "what a non-trivial class decorator looks like in practice." Skim once, focus on `_process_class` and `_create_fn`.
- Watch Raymond Hettinger's PyCon 2017 talk ["Modern Python Dictionaries"](https://www.youtube.com/watch?v=npw4s1QTmPg) — about 50 minutes. Tangential to this week's topic but covers the `__dict__` machinery descriptors live on top of. Free on YouTube.
- Watch Raymond Hettinger's PyCon 2013 talk ["Class Development Toolkit"](https://www.youtube.com/watch?v=HTLu2DFOdTg) — about 60 minutes. The canonical Hettinger talk on properties, descriptors, and `super()`. Free.
- Watch David Beazley's PyCon 2013 talk ["Python 3 Metaprogramming"](https://www.youtube.com/watch?v=sPiWg5jSoZI) — about three hours. The deepest free talk on metaclasses and descriptors. Skim with a notebook.
- Read [PEP 681](https://peps.python.org/pep-0681/) ("`dataclass_transform`") — about 15 minutes. How type checkers learn that a class decorator behaves like `@dataclass`.
- Read [the `attrs` source](https://github.com/python-attrs/attrs/blob/main/src/attr/_make.py) — about 2,500 lines. The mature, production-grade alternative to `dataclasses`. Compare `attrs.define`'s class-decorator design to `dataclasses.dataclass`'s.
- Read [the `pydantic` v2 model source](https://github.com/pydantic/pydantic/blob/main/pydantic/main.py) — pydantic v2 uses a metaclass (`ModelMetaclass`) plus `dataclass_transform`. The reference for "production-grade metaclass". ~30 minutes.
