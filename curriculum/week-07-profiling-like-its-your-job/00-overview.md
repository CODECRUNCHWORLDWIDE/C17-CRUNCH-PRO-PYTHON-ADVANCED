# Week 7 — Profiling Like It's Your Job

> *Four tools. Two paradigms. One discipline. `cProfile` is a deterministic, function-level instrument: every `CALL` and `RETURN` bytecode is intercepted, every call edge timed, every result aggregated — accurate, but ~30% slower than untraced and biased toward whatever calls a lot of functions. `line_profiler` is a deterministic line-level instrument: per-decorated-function, every line's hit count and elapsed time recorded — surgical, but you must choose where to point it. `py-spy` (Ben Frederickson, 2018) is a sampling profiler that attaches to an already-running PID via `process_vm_readv` / `task_for_pid` and reconstructs Python stacks from outside the interpreter — production-safe, zero target modification, ~1% overhead at 100 Hz. `scalene` (Berger et al., UMass, 2020) is a sampling profiler that separates CPU time spent in pure Python from time spent in C extensions and additionally samples memory allocations via a custom allocator — the right tool when "is this CPU- or memory-bound" is the actual question. **This week you learn when each is the right answer, and you produce a profile-and-fix report on a real piece of open-source Python.***

Welcome to Week 7 of **C17 · Crunch Pro Python Advanced**, and the first week of Phase 3 (Performance & Native Code). Week 6 left you with the concurrency decision tree and a `concurrency-bench` artifact whose memo defends every primitive choice with wall-clock numbers. That memo only works because you measured. This week sharpens the measurement itself.

The thesis is small: **before you optimise anything, profile it.** The corollary is large: **most profiling that engineers do is wrong, and the conclusions that follow are wrong with it.** You will spend the week learning to distinguish the bottleneck that *looks* expensive (the function with the biggest `cumulative` column) from the bottleneck that *is* expensive (the function whose `tottime` column says it is hot, but only on the input distribution you actually serve). You will learn why sampling and instrumentation give different answers, when to trust which, and what "the heisenberg problem" looks like in a Python profile. By Sunday you will have a portfolio piece: a public, written profile of a real OSS Python project, with a flamegraph, a numbered hot path, and a defensible recommendation.

The four tools cover the full grid. `cProfile` (originally Roger Bauer's `_lsprof`, 2002; landed in 2.5; `cProfile` is the C-accelerated wrapper around it) is a **deterministic** profiler: it traces every Python function call via `sys.setprofile` and records start/end times. The output is exact down to the call edge. It is the right tool when you want a function-level accounting of where time goes in a CPU-dominated workload you can run locally with the profiler attached. It is the wrong tool when the workload only misbehaves in production, when the call graph is so dense that the profile is dominated by tracing overhead, or when the question is about lines within a single function rather than functions within a call tree.

`line_profiler` (Robert Kern, 2008; maintained today by Pyutils) is the line-level complement. You decorate the functions you care about with `@profile` and run under `kernprof -l -v`. The output is per-line: number of hits, total time, time per hit, percentage. It is the right tool when `cProfile` has told you the hot function and now you need to know which *line* inside it is the cost. It is the wrong tool when you do not yet know which function to point it at, or when the workload's hot path crosses many small functions.

`py-spy` is the production tool. Built in Rust by Ben Frederickson (formerly of Spotify and OkCupid) on a 2017 prototype that became the present project in 2018, py-spy attaches to a running Python interpreter — *without* requiring you to add a `-m cProfile` to its launch line, without restarting it, without inserting any instrumentation. It reads the interpreter's memory across the address-space boundary (`process_vm_readv` on Linux, `task_for_pid` + `vm_read` on macOS) and reconstructs Python stack frames from the `PyFrameObject` / `_PyInterpreterFrame` layout. At a 100 Hz sampling rate, overhead is typically under 1% — low enough to leave attached for hours on a production process and capture an honest sample of where wall-clock time goes. The output renders as a flamegraph (`py-spy record -o flame.svg --pid PID`) or as a `top`-style live view (`py-spy top --pid PID`). Repository: <https://github.com/benfred/py-spy>.

`scalene` is the memory-and-CPU tool. Developed in the PLASMA lab at UMass Amherst (Emery Berger, Sam Stern, Juan Altmayer Pizzorno, 2020) and continuously improved since, scalene is also a sampling profiler — but it adds two things `py-spy` does not. First, it distinguishes CPU time spent in **pure Python** from CPU time spent in **C extensions**, with line-level granularity. This is the single most useful diagnostic in modern Python performance work, because the right fix for a Python-line bottleneck (rewrite the loop, vectorise, JIT) is different from the right fix for a C-line bottleneck (different algorithm, different library, batch larger). Second, scalene samples **memory allocations** via a custom allocator (`scalene-1.5+` uses `libscaleneallocator.so` injected via `LD_PRELOAD`) and attributes them to source lines. If your slow function is slow because it allocates 200 MB of intermediate lists per call, scalene tells you which line, in numbers. Repository: <https://github.com/plasma-umass/scalene>.

The fifth piece of the toolkit — not a profiler, a *visualisation* — is the **flamegraph**, Brendan Gregg's 2011 invention (Netflix). A flamegraph is a stacked horizontal bar chart of sampled stacks: the x-axis is "percentage of samples," the y-axis is "stack depth." Tall, narrow towers are deep call paths; wide plateaus are hot frames. The discipline of reading a flamegraph — "the widest plateau at the top of a tower is the hot leaf; the path beneath it is how you got there" — is the same whether the samples came from `py-spy`, `scalene`, `perf`, or `dtrace`. The visualisation is so good that the rest of the industry quietly adopted it. We will treat flamegraphs as a first-class artifact in this week's mini-project.

We will also, deliberately, **not** chase every shiny tool. `austin` is excellent but redundant with `py-spy` for this curriculum. `yappi` is solid for asyncio profiling but covered briefly only. `memray` (Bloomberg) is the right memory profiler for production memory leak hunts but overlaps with scalene's memory mode; we cite it. The IDE-bundled "profilers" in PyCharm and VS Code are wrappers around `cProfile`. The new `sys.monitoring` API (PEP 669, landed 3.12) is the future of CPython profiling and is the C-level substrate `py-spy` 0.4+ optionally uses; we cite the PEP. The point of the week is *fluency in a small toolkit applied with judgement*, not breadth.

Two paradigms anchor the week. **Sampling** profilers (py-spy, scalene, the new `sys.monitoring`-based tools) interrupt the program at a fixed rate (typically 100–1000 Hz) and record the current stack. The result is a statistical estimate of where time is spent, with overhead proportional to (sample rate × work-per-sample), independent of how many functions you call. Sampling profilers handle production loads, deep call graphs, and long-running processes well. They do not capture every call — *by design* — but they capture enough that the hot path emerges from the noise after a few seconds of data.

**Instrumentation** profilers (cProfile, line_profiler, the old `profile.py`) intercept every function entry and exit, record exact times, and produce a deterministic accounting. The result is exact for the trace you collected, but the act of measuring slows the program by 20–40% — and worse, it slows function calls *more than it slows function bodies*, which biases the profile toward call-heavy code and away from compute-heavy code. The "heisenberg problem": measuring perturbs what you measure. We will see this in the wild in Lecture 1.

The deliverable for the week is a **profile-and-fix report**. You pick a real, free, open-source Python project — Flask, requests, the `json` test corpus runner, the `markdown-it-py` benchmark, the `bandit` linter, the `pyflakes` AST walker, anything 1k–20k lines that you can install and run a representative workload against. You run `cProfile`, you read the output, you locate the hottest function. You add `@profile` decorators and run `line_profiler`, you find the hottest line. You attach `py-spy` to the project running in a separate process, you produce a flamegraph. You run `scalene`, you identify whether the bottleneck is pure-Python time or C-extension time or memory pressure. You then write a 600–900 word report that names the hot path, justifies it with numbers, proposes a fix (one paragraph; you do not have to implement it), and includes one flamegraph SVG and one cProfile table. The report is the artifact you point at when an interviewer asks "tell me about a time you profiled and fixed something." Free, open, public, with numbers.

## Learning objectives

By the end of this week, you will be able to:

- **Distinguish** sampling from instrumentation: explain the cost model of each, predict which produces a higher overhead on a given workload, predict which is biased toward what, and choose between them on first principles. Cite `cProfile`'s use of `sys.setprofile` (deterministic, in-process) versus py-spy's use of `process_vm_readv` (sampling, out-of-process).
- **Read** a `cProfile` table without consulting the docs: interpret `ncalls`, `tottime`, `percall`, `cumtime`, `percall`, distinguish `tottime` from `cumtime`, sort intelligently (`-s tottime`, `-s cumulative`), and explain why the function at the top of the `cumulative` sort is almost never the one you should fix. Cite <https://docs.python.org/3/library/profile.html>.
- **Drive** `line_profiler` (`kernprof -l -v script.py`) on a function you have already isolated via `cProfile`. Interpret the per-line output: `Hits`, `Time`, `Per Hit`, `% Time`. Explain why `line_profiler` reports time in different units depending on the host clock resolution.
- **Attach** `py-spy` to a running Python process: `py-spy top --pid PID` for live triage, `py-spy record -o flame.svg --pid PID --duration 30` for a flamegraph, `py-spy dump --pid PID` for a one-shot stack of a stuck process. Cite the py-spy README and the security model (Linux: `ptrace_scope=1` requires the same UID or `sudo`; macOS: requires `sudo` or signed binary).
- **Run** `scalene` on a workload and interpret its three-column output: native time, Python time, system time. Identify a memory-bound bottleneck via the allocation column. Compare to `py-spy`'s output on the same workload and explain the difference. Cite <https://github.com/plasma-umass/scalene>.
- **Read** a flamegraph: identify the hot leaf (widest plateau at the top), the hot call path (the column beneath it), and the "diffusion" pattern (a wide base with no narrow top — your time is spread across many shallow calls, not stuck in one place). Cite Brendan Gregg's 2011 paper / blog.
- **Articulate** the heisenberg problem: profilers perturb their target, instrumentation perturbs more than sampling, the perturbation is non-uniform (function-call code is hit harder), and the canonical mitigation is to compare *relative* costs within a single profile run rather than absolute times across runs.
- **Choose** the right tool for the symptom: production stall → py-spy attach; "where is the time going" on a CPU workload locally → cProfile; "which line inside this function" → line_profiler; "is this CPU or memory" → scalene; "show me a picture I can put in a memo" → flamegraph from py-spy or scalene.
- **Diagnose** the three canonical profiling failures: (1) optimising the wrong function (the cProfile table's top entry by `cumulative` is `<built-in method builtins.exec>`, you "optimise" it, nothing changes); (2) measuring the warm-up phase (you profiled a 10-second run that included 8 seconds of module import); (3) measuring an unrepresentative workload (you profiled on 100 rows of input; production has 100 million).
- **Cite** the relevant PEPs and source files: PEP 657 (fine-grained location for tracebacks, 3.11; relevant because profilers now report instruction-level positions), PEP 669 (`sys.monitoring`, 3.12; the new low-overhead profiling API), `Lib/cProfile.py`, `Modules/_lsprof.c`, the py-spy and scalene READMEs.

- A working CPython **3.11 or newer** (3.13 preferred). PEP 657 line/column tracking landed 3.11; PEP 669 `sys.monitoring` landed 3.12 and is what py-spy 0.4+ can optionally piggyback on.
- Optional: install `line_profiler` (`pip install line_profiler`), `py-spy` (`pip install py-spy`), `scalene` (`pip install scalene`), `snakeviz` (`pip install snakeviz`, optional cProfile visualiser), and `flameprof` (`pip install flameprof`, an alternative flamegraph renderer). All are pure-Python or pip-installed binary wheels; none requires a compiler.
- A machine with at least 2 CPU cores. Most profiling discussions assume one core for the program and one for the profiler, even though sampling profilers do not require this. Single-core VMs introduce sampling artifacts.
- The ability to run a Python process for 30+ seconds against a representative workload. If your project finishes in 0.2 seconds you cannot sample it meaningfully — you scale it up first.

## Topics covered

- **What profiling actually measures** — wall-clock time vs. CPU time vs. on-CPU time vs. off-CPU time. Why `time.time()` and `time.perf_counter()` measure different things, and why `time.process_time()` is the one that excludes sleep. The heisenberg problem and its mitigations.
- **Sampling vs. instrumentation** — The cost model of each. The bias each introduces (sampling biases toward long-running frames; instrumentation biases toward call-heavy code). The thresholds at which one becomes preferable. The historical arc: from `profile.py` (pure-Python instrumentation, 1994) to `cProfile`/`_lsprof` (C instrumentation, 2005) to py-spy (sampling, 2018) to PEP 669 (low-overhead monitoring API, 2023).
- **`cProfile` end-to-end** — `python -m cProfile -s cumulative script.py`, `python -m cProfile -o out.pstats script.py`, reading the output programmatically with `pstats.Stats`, `Stats.strip_dirs().sort_stats('tottime').print_stats(20)`. The columns: `ncalls`, `tottime`, `percall_t`, `cumtime`, `percall_c`. The "tottime is *exclusive*, cumtime is *inclusive*" rule. Why sorting by `cumulative` makes you optimise `<module>`; why `tottime` is almost always the right sort. Cite `Lib/cProfile.py`, `Modules/_lsprof.c`, <https://docs.python.org/3/library/profile.html>.
- **`line_profiler` and `kernprof`** — The `@profile` decorator (injected at runtime; not imported from anywhere). `kernprof -l -v script.py`. The output. Why this is the second tool, not the first. Cite the line_profiler README.
- **`py-spy` in depth** — Subcommands: `record`, `top`, `dump`. Sampling rate (`--rate 100`). Idle time (`--idle`). Native stacks (`--native`, requires Rust toolchain at install). Subprocess tracing (`--subprocesses`). Output formats: flamegraph SVG (default), speedscope JSON, raw. Attaching to processes you don't own (Linux `ptrace_scope`, macOS code signing). Cite <https://github.com/benfred/py-spy>, the README's "FAQ" section.
- **`scalene` in depth** — Pure-Python CPU vs. native CPU vs. system time. Per-line attribution. Memory allocation sampling. The `--cli` mode for non-Jupyter use. The web report. Limitations: scalene can disagree with cProfile because it samples, and disagree with py-spy because it has access to interpreter internals that py-spy does not. Cite <https://github.com/plasma-umass/scalene>, the Berger et al. PLDI 2023 paper.
- **Flamegraphs** — Brendan Gregg's 2011 design. Reading a flamegraph: the x-axis is sample count (not time), stacks are sorted alphabetically not by sample order, height is stack depth, width is hotness. The "icicle" inverted variant (`--inverted` on py-spy). Diff flamegraphs for before/after comparisons. The `flamegraph.pl` Perl script is still the canonical renderer for `perf` data; py-spy and scalene render SVG directly. Cite <https://www.brendangregg.com/flamegraphs.html>.
- **Choosing the right tool for the symptom** — A decision table you commit to memory by Sunday: production stall → py-spy attach; CPU local → cProfile; line-level → line_profiler; memory → scalene or memray; "before/after" → diff flamegraphs.
- **Reading a profile, finding the actual bottleneck** — The discipline: name the hot leaf, name the hot path, predict the fix, measure the fix, accept or reject. The trap of "the obvious-looking bottleneck": the function that *appears* expensive because its name is in red in your IDE, vs. the function that *is* expensive because it is in the top of `tottime`. Two case studies (one a JSON-heavy hot loop, one a regex-quadratic blowup).
- **Making it faster** — Once you have the hot path, the fix usually falls into one of four categories: (1) algorithm change (O(n^2) → O(n log n)); (2) data-structure change (list → set for membership); (3) library replacement (`json` → `orjson`; `re` → `regex` with possessive quantifiers); (4) work elimination (memoise, cache, batch). We will see one of each by example.

## Stretch

- Build `py-spy` from source: `git clone https://github.com/benfred/py-spy && cargo build --release`. The 5-minute Rust build is itself an education; you see the FFI to `libpython` and the OS-specific `read_process_memory` modules (Linux, macOS, Windows) wired up. The codebase is ~5000 lines of Rust and is unusually readable.
- Read PEP 669 (`sys.monitoring`, 3.12) end-to-end (~40 minutes). The new low-overhead monitoring API is the foundation for the next generation of profilers; py-spy 0.4+ and yappi and scalene are all moving to it. The "tool ID" architecture (multiple tools can monitor without colliding) is the production-grade improvement over `sys.setprofile`. <https://peps.python.org/pep-0669/>.
- Read PEP 657 (fine-grained tracebacks, 3.11) (~20 minutes). Every profiler output in 3.11+ benefits from the column-level location data PEP 657 added. The cProfile output's filename:lineno annotations now point to the *expression* not just the line. <https://peps.python.org/pep-0657/>.
- Read Brendan Gregg's *Systems Performance* (Pearson, 2020), Chapter 6 "CPUs" §6.5 (Profiling) (~30 minutes if you have access; the chapter is ~50 pages but §6.5 is ~10). The same principles apply across OS-level and language-level profiling.
- Watch Emery Berger's PyCon 2022 talk "Scalene: A High-Performance, High-Precision CPU+GPU+Memory Profiler for Python" (~40 minutes): <https://www.youtube.com/results?search_query=emery+berger+scalene+pycon+2022>. The motivation section explains why CPU vs. native vs. memory needed to be three separate columns, and the live demo of finding a 100x speedup is worth the price of admission.
- Read [py-spy's source](https://github.com/benfred/py-spy/tree/master/src) — start with `src/python_process_info.rs` (the version-detection logic; py-spy supports 2.3 through 3.13) and `src/python_interpreters.rs` (the struct layouts py-spy reads from). About 30 minutes.
- Read [`Lib/cProfile.py`](https://github.com/python/cpython/blob/main/Lib/cProfile.py) (~200 lines) and [`Modules/_lsprof.c`](https://github.com/python/cpython/blob/main/Modules/_lsprof.c) (~1100 lines). The Python wrapper is short; the C implementation is the interesting bit — note how it uses `PyEval_SetProfile` to register the per-call callback, and how the `roptimes` array accumulates per-edge timing. About 45 minutes.
- Read [scalene's PLDI 2023 paper](https://dl.acm.org/doi/10.1145/3591260) "Triangulating Python Performance Issues with `Scalene`" by Berger, Stern, Altmayer Pizzorno (~25 minutes). The paper explains the *why* of separating Python/native/memory, with measured case studies.
